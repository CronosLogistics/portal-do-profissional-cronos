## Server integration rules (src/lib)
- Official documents are recursively projected from the fixed Qualidade and Modelo Documental folders through the corporate Graph connection, behind active-user authentication; manual links remain separate. Why: reflect official documents without exposing credentials or accepting arbitrary folder requests.
- Vacation consultation reads projected SharePoint scheduling fields server-side for active portal users, exposes only active collaborators' absence dates and substitutes the extra-days return when populated; it never exposes HR notes or entitlement data. Why: shared absence consultation must not leak unrelated personnel information.
- Daily Entra sync lives in `src/lib/entra-sync.server.ts` (pure rules in `entra-sync.rules.ts`), triggered by the managed schedule calling `/api/public/jobs/entra-sync` or an admin's `syncNow`; it matches by `entra_oid` (email only before linking), mirrors name/email/employee ID/accountEnabled, bans disabled accounts, and records the run (origin, who triggered it) in the singleton `status_sincronizacao`, guarded by a 10-minute `reservar_sincronizacao` lock. Why: Microsoft is the source of truth for professionals.
- Monthly praise compilation (D2): Power Automate POSTs `{mes_ano, html}` to `/api/public/compilado-elogios` with `X-Webhook-Secret` (secret `COMPILADO_WEBHOOK_SECRET`); `receber_compilado` (service_role only) stores the raw HTML in `compilados_elogios` (outside `avisos.mensagem`, so the sanitizer can't break it) and upserts one `tipo='compilado'` aviso per month; slide 4 reads `compilado_vigente()` (1 month) and the reader shows the HTML in a script-less sandboxed iframe. Why: keep the email's full layout safely.
- Praise (D1) reads SharePoint RQ0013 server-side only (`src/lib/feedback.server.ts`, 5-min cache), resolves AuthorLookupId through the site's User Information List with createdBy identity fallback, and filters in `feedback.rules.ts` by the caller's profile email: involved rows or rows where they are the GESTOR_CONSIDERACOES person; only `field_4 = 'Elogio - EL'`. Why: the browser never gets the token or other people's rows, and the author and manager come from SharePoint.
- OfficeContext resolves the caller's verified profile email through projected SharePoint corporate-person lookup and active status server-side, never localStorage. Why: display only the professional's actual office.
- Priority queries return the caller's own rows and, separately, rows of department-authorized subordinate emails from `meu_escopo_departamento` (excluding own rows; reports never inherit the leader's GP access); the nav badge counts own rows only. Why: leaders consult reports in a separate tab without inflating their personal count.
- People-management priorities use projected SharePoint fields and the department scope RPC for own/subordinate emails and Gestão de Pessoas membership; system admin alone never grants all RH rows. Why: department replacement must not preserve stale GP access through legacy profile names.
- Department sync reads projected Departamentos, Profissionais Brasil current-department lookup (hiring-department fallback only when empty) and corporate-person lookups server-side, applies profiles and leadership relations atomically through service-role-only RPCs, refreshes at login and daily Entra sync, and uses a persistent five-minute freshness/lease check. Why: transfers and new hires receive authoritative sector access without names, browser input or manual assignments defining privileges.
- Manager feedback received uses a separate authenticated function: resolve Profissional_ID through Profissionais Brasil and its corporate-person lookup to the active caller's verified email; never match names or broaden by role, and render comments as plain text. Why: recipient privacy is separate from RH priority access and external HTML cannot execute.
- The manager-feedback function also returns author-scoped open records through `pessoasDoUsuario` with no global RH bypass; the page separates received messages from author tasks linking to SharePoint editing. Why: reuse priority completion rules without confusing sender and recipient visibility.
- Priority category and group visibility uses the shared pure `temPendencias` predicate; consultation errors render independently of empty accordions. Why: hide empty navigation consistently without hiding integration failures.
